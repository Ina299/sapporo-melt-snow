区域と直行経路の改善（2026-09-08、2026-09-09 更新）

2026-09-09 更新：市内限定と8時間シフト

作業対象を札幌市境（OSM行政界）の内側の方向区間に限定し、各車両の経路を8時間のシフトに分けた。1シフトは所在地を出て作業し、帰庫までを8時間以内に収める。次のシフトは所在地から再出庫する。休憩・給油・交代の時間は未算入。対象431,116区間のうち市外128,767区間を対象外とし、市内302,349区間のうち300,081区間を割当、2,268区間は往復到達を確認できず未割当。作業延長は12,345.60方向km。

2026-09-09 追記（再計算待ち）。 市境の内側でも朝里ダム上流などの未舗装の山道（OSMで surface が dirt・gravel 等の未舗装、または tracktype 付き、175路線）が作業対象に入り、手稲の所在地から約17km離れた山中の数百mの区間へ回送する経路が生じていた。除雪対象と考えにくいため src/routing.py でこれらを道路網から除外した。あわせて、表示用の作業単位を切り出す際に回送だけの単位（378件）が生じていたので、隣の作業単位へ統合する。さらに、シフトを車両の一筆書き（Euler閉路）の8時間ごとの時間切りで作っていたため、閉路が区域内を行き来する分だけ1シフトの作業が飛び地になっていた。これを、車両の区域をシフト数ぶんの連続した小区域に二分割（bisect_groups）し、小区域ごとに所在地から出発して帰庫する郵便配達人経路を作る方式に変えた。シフト数は作業時間÷（8時間×0.85）から始め、出庫から帰庫までが8時間を超える小区域があれば数を増やして繰り返す。シフトの順番は所在地から近い小区域から。市域閉路と配車の再計算後に本書の数値を更新する。

回送が旧対象の2,111kmから4,923kmへ増えたのは、シフトごとに所在地へ戻り再出庫する往復が加わったため。1シフトの平均は約7.4時間。会社担当固定方式は3台のKRSに市南部の広い区域が集まり、1台あたり28シフトを要する。前版（市外を含む対象・帰庫なしの一筆書き）の数値は以下に比較用として残す。現行データは python scripts/improve_dispatch.py で再生成する。

この節の作業対象の被覆は全方式で421,029方向区間。対象431,116区間のうち10,087区間は未到達（市外を含む旧対象）。作業延長は18,063.91方向kmで変わらない。旧回送距離は保存した総車両時間から作業時間（作業延長÷8km/h）を引き、回送速度20km/hで換算したもの。同じ時間・距離モデルによる厳密な復元だが表示は丸めている。

車両ごとの担当区域（2026-09-08 追加）。 中間版は会社の全作業を1本の最寄り順路で回り、それを累積時間で車両に切っていた。最寄り順路は取り残した作業を後で拾いに戻るため、後半の車両ほど担当が市内各所に散る飛び地になった。飛び地をなくすため区域を先に作る方式に変え、5段階で回送を詰めた。

  1. 扇形版：所在地を中心とした方位で車両数ぶんの扇形区域を作り、各区域で作業単位ごとに最寄り順。飛び地は消えたが回送は3,425km（中間版1,869km）に増えた。回送の内訳は作業間の接続2,859km、帰庫445kmで、接続が約1万1千件あり1件0.25kmでも積み上がっていた。
  2. 断片・Or-opt：市域閉路で連続していた作業は前の終点が次の始点なので接続コストがゼロ。閉路の連続部分を「断片」として崩さず、断片単位で最寄り順に並べ、作業終点から近い40作業までの道路コスト表を使って1〜3断片を移動するOr-optで接続を短縮（nearest_k_costs・improve_order）。接続は1,847件に減ったが、細長い扇形が閉路を細切れにするため1件1.4kmと長く、3,162km。
  3. 二分割区域：作業時間が均等になるよう地理的な二分割を繰り返してブロック状の区域を作る（bisect_groups）。閉路の断片が長く残り、接続1,262件・1,902kmで、全社方式の回送は2,679km、完了91.41時間。
  4. 現行・区域別郵便配達人：市域全体の閉路を切った断片をつなぐのをやめ、各区域の担当区間だけを対象に経路を作り直す。出入りの数が合わない交差点を道路最短経路の回送で補い（不足側から余剰側への輸送問題を最小費用流で解く）、つながった成分ごとにEuler閉路を作り、成分を所在地から最寄り順に接続して帰庫する。表示用の作業単位は出来上がった一筆書きを約15分ごとに切り出す。全社方式の回送は2,185km、完了89.58時間。
  5. 現行・成分の訪問順の最適化：区域内の成分間の道路コスト表（最も近い節点同士の有向コスト）と帰庫コストを使い、成分の訪問順を最寄り順の後にOr-opt（1〜3成分の移動）で改善する。全社方式の回送は2,111km、完了89.34時間。中間版（飛び地あり）との差は約242kmまで縮まった。

残る回送の内訳（全社方式）は出庫236km・帰庫343km・区域内の接続と成分間の移動1,532km。鹿島は所在地（南区中の沢）から離れた13区域へ往復するため1,207kmと最大で、所在地の位置そのものが要因。区域境界での区間交換、複数拠点からの出発は未実施。会社担当固定方式の台数変更（1〜標準台数）は、全シナリオの経路を持つと画面データが131MBになるため廃止し、両方式とも標準台数だけを計算する。

回送削減の大部分は旧モデルで強制していた頻繁な帰庫を外した効果。実際の除雪運用に対する削減率ではない。所在地への近さだけで割り当てると、台数の少ない会社に広い区域が集まって完了が遅れる。全社方式は区域境界を調整して負荷の偏りを抑える。いずれも休憩・補給・交通規制・機種別性能・雪量を反映した実運行ではなく、6時間内の運用としては不成立。

アルゴリズム

  1. 既存の有向道路閉路を、15分または開始点からの半径750mを目安として小さい連続作業へ分割。単一の長い道路区間はさらに分割しないため、絶対的な区域径の保証ではない。11,151作業単位を割当対象とする。会社への割当後、各会社の作業を作業時間が均等になるよう地理的に二分割を繰り返して車両数ぶんの連続した区域に分け、区域ごとに担当区間の郵便配達人問題を解いて一筆書きの経路を作る。
  2. 各単位の開始・中間・終了ノードについて、各社の出発点からの往復道路時間の平均を計算。所在地優先方式ではこの値が最小の会社に割当。
  3. 全社方式では会社ごとの加算重みを調整する。割当の基準は 往復道路時間＋会社の重み。台数当たり作業時間が大きい会社の重みを増やし、120回の試行から最大の台数当たり作業時間が最も小さい割当を採用する。瞬間的な空き時間で離れた作業を配るのではなく、固定した重みで区域境界をまとめて動かす。
  4. 各社の現在地から、未作業の開始ノードのうち道路上で最も近いものをDijkstra法で探索。そこへ直行し、作業終了点から次を探索する。直線距離の近さだけで順番を決めない。
  5. この連続した順序を、累積時間に応じて車両数へ分割する。各車両は担当列の最初へ出発し、途中は直接移動し、最後から帰庫する。道路構造上、会社の前を偶然通過する可能性はあるが、中間の帰庫を強制しない。

区域が必ず連結になること、車両数の最適性、巡回順の全体最適性は保証していない。往復道路距離・近傍順序・連続分割によって飛び地と長距離回送を抑える設計である。現行の区域は実契約区域ではなく「仮の割当」。未割当区間や市外対象は引き続き明示する。

検証と再現

全区間の重複割当ゼロ、未割当との完全な区分を検証。各台数シナリオの全経路について、有向道路の合法性・作業間の連続性・出発点への帰着・作業単位の欠落ゼロを検証した。単体テストは道路上の最寄り探索と、地理的な順序を崩さない車両分割を確認する。

python scripts/improve_dispatch.py
python -m unittest discover -s tests -v

dispatch*.json と joint_dispatch*.json、画面用の同名データを更新する。データの route_format は direct_jobs。各会社の trips は作業本体と直前作業からの接続を共有し、各車両は head_features → 1番目の本体 → 2番目以降のincoming_features＋本体 → tail_features の順にたどる。車両の最初の作業では、他車両から続く接続を使用しない。

gzipの順序付き経路も更新した。jobs に作業本体と直前作業からの原本道路キー付き接続、scenarios に各車両の作業ID順と出発・帰着経路を保存する。旧版の配列形式と異なるため route_format とこの仕様を確認する。旧スクリプト run_dispatch.py は比較再現用で、現行データの生成には improve_dispatch.py を使用する。
