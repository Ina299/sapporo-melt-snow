# 堆雪・排雪・融雪の日別収支モデル

道路脇に残す雪、近接の一時堆雪、雪堆積場への搬出、DCでの融雪を分けて計算する。全量を融雪点へ運ぶ前提を置かず、道路の置き場と車両・施設の能力に応じて雪を翌日に持ち越す。[画面の「堆雪と搬出」](../web/index.html#snow-management)で操作できる。

これは選択観測点の実降雪を使う仮定道路群の感度分析。市全体・行政区全体の需要推計、特定のDC候補地の効果、運用可能な実配車を認定したものではない。

## 公開資料と仮定の境界

[札幌市の新雪除雪の説明](https://www.city.sapporo.jp/kensetsu/yuki/josetsu_info.html)では、新雪を道路脇へ寄せる作業と、路面整正・拡幅・運搬排雪が区別されている。[雪対策施設の説明](https://www.city.sapporo.jp/kensetsu/yuki/yukishisetsu/index.html)では、運搬された雪を貯める雪堆積場と融雪等の施設が説明されている。[雪堆積場の利用案内](https://www.city.sapporo.jp/kensetsu/yuki/taisekijou/index.html)には受入時間や一時閉鎖などの条件がある。これらを踏まえて複数の処理経路と有限の受入枠を設けた。各場の最新の運営枠・閉鎖情報を接続したわけではない。

| 入力 | 根拠・扱い |
|---|---|
| 日別降雪 | 取得済み2025年度の市内13観測点。2025-11-01〜2026-04-10の161日。原本・取得記録は既存のweatherデータとsources.json |
| 道路延長・除雪対象幅 | 利用者が仮定する対象面積。OSMの方向区間の延長をそのまま面積へ転用しない。同じ道路の往復を二重計上しない |
| 道路脇・一時堆雪の余地 | 入力仮定。実測した歩道・車道幅、出入口・交差点の見通しを確認していない |
| 密度 | 新雪100kg/m³、堆雪・運搬雪400kg/m³が初期仮定。観測した深さから質量への換算には新雪密度を使う |
| ダンプ | この道路群に使用する仮定台数。KRS等のショベル台数や市の必要ダンプ台数から自動転記しない |
| 距離・時間 | 片道距離、速度、積込・投雪・待機の入力仮定。除雪車の作業経路ではなく排雪運搬の条件 |
| 堆積場・DC | この道路群へ配分する日受入量・貯留枠・熱・排水。実施設の公表総能力を独占利用できるとは仮定しない |
| 自然融解 | 全屋外在庫に適用する日定率の感度パラメータ。初期0％。気温・雨・日射に基づく予測ではない |

観測値には原資料の参考値期間が含まれる。画面とJSONに注記を維持する。欠測・負の降雪・日付の欠落を0で埋めずエラーにする。現在の降雪系列に欠測はない。積雪深の減少をそのまま融解量にせず、圧密による体積変化と質量の消失を区別する。

## 日別の計算

内部は全てトンで保持する。日降雪量は `道路延長(m) × 除雪対象幅(m) × 降雪(cm)/100 × 新雪密度(kg/m³)/1000`。例えば1km・幅10m・新雪10cm・100kg/m³なら100t。堆雪容量は `体積(m³) × 堆雪密度/1000` でトンへ換算する。圧密は質量を減らさない。

初日在庫は0。各日は以下の順に処理する。

1. 前日から残る道路脇・一時堆雪・雪堆積場の雪に、設定した自然融解率を適用する。DCの融雪待ち在庫は、当日の熱・排水上限まで先に融雪する。
2. 当日の新雪を道路脇へ追加する。除雪そのものは当日中に実施できたと置く。新雪除雪の出動基準や路面の圧雪はこのモデルでは再現しない。
3. 道路脇が上限の80％を超えると、50％へ減らす量を搬出対象にする。80％・50％は計算上の方針で、市の出動基準ではない。
4. 近接一時堆雪に空きがあれば、ローダーの日移動能力以内で移す。その後、道路からの必要搬出を優先し、一時堆雪の雪も外へ運ぶ。
5. 受入可能な搬出先を所要時間順、またはDC優先で選び、ダンプごとの残り時間で完了できる往復便を割り当てる。部分積載でも1往復分の時間を計上する。
6. どこにも運べない雪は元の在庫に残す。道路上限を超えた雪も消去せず、日末超過量・超過日数として記録する。

近接一時堆雪はローダーで扱える隣接の使用可能な置き場を仮定している。離れた空地への移送を無料で計上するための枠ではない。遠隔地へ一度運び、後日別施設へ再搬出する二段階のダンプ輸送は未実装。

## 車両と受入施設の制約

1便の積載量は重量上限と荷台容積×堆雪密度の小さい方。所要時間は `片道距離×2/速度＋(積込＋投雪＋待機)/60`。各車両に1日分の時間を配り、往復を終えられる場合だけ運ぶ。初期値は2台・各8時間、8t・20m³、20km/h、積込20分・投雪8分・待機20分。全て感度値で、運転実績ではない。

雪堆積場は日受入枠と残り貯留枠を両方制約にする。自然融解率0％なら季節を通じて有限の貯留量を消費する。自然融解があればその分だけ翌日の空きが戻る。搬入だけで処理完了・消失とは数えない。

DCの熱上限は既存の熱モデルと同じ式。初期は、この道路群に配分するIT容量0.5MW・稼働率90％・回収率80％・雪−5℃・排水2℃・24時間。`有効熱(MW)×86,400 / (333.5＋2.1×|雪温|＋4.186×排水温)` でt/日を求める。IT全体の設備容量と、この道路群に配分する熱は区別する。

日融雪量は熱上限と排水枠の小さい方。日搬入量は、日受入枠と「当日残る融雪能力＋未融雪貯留の空き」の小さい方以下にする。融雪できない分はバッファに残す。熱または排水が0ならDCへの新規搬入を止める方針。既存槽の処理能力とDC熱上限を単純加算しない。

1日内の流入順序と処理をまとめたモデルのため、投雪レーンやローダーの同時稼働、時間帯ごとの渋滞・待ち行列・夜間受入は再現しない。入力待機時間は固定値である。搬出先の選択は日ごとの貪欲法で、将来の大雪に備えた貯留予約や費用の全期間最適化ではない。

## 比較と読み方

同じ降雪・道路・ダンプ・堆積場条件で「堆積場のみ」「堆積場＋DC」「搬出先をDCに限定」を並べる。どの方式でも道路脇の堆雪は許容する。DCを追加して搬出量が増えれば、総走行も増える場合がある。雪を運べず放置する方式の走行距離が短くても、それだけで優良な方式とは判断しない。上限超過と道路・一時残雪を先に比較する。

期末収支は `累積発生＝道路脇＋一時堆雪＋雪堆積場＋DC未融雪＋累積DC融雪＋累積自然融解`。搬出量は移動した量なので右辺に加えない。毎日の収支誤差も検証する。自然融解率0％の初期値では春の残雪が過大になり得るため、通年の実残雪予測とは呼ばない。

日末の超過は仮定した置き場に収まらない質量で、実際の交通閉塞を直接示す指標ではない。新雪追加直後の超過もJSONに保存するが、画面の超過日数は搬出後の日末で数える。

## 再現・検証

`npm run build:snow` で取得済み降雪から入力データを再生成する。`npm run test:snow` が質量保存、有限貯留、積載重量・容積、往復時間、DC待ち在庫、熱・排水停止、自然融解、欠測拒否と全13系列を検証する。`npm test` は画面の比較・入力変更・無効入力・JSON保存・モバイル幅を確認する。

画面のJSON保存は入力全項目、観測点・注記、日別収支、比較サマリーを含む。共通計算実装は [snow-model.js](../web/snow-model.js)、取得済み降雪の小さな配信用データは [snow_management.json](../data/processed/snow_management.json)。画面とNodeテストで同じ計算関数を使う。

実道路計画へ進めるには、路線ごとの対象幅・堆雪余地・積込場所、各施設の入口・日別共有枠・開設日、ダンプとローダーの配置・稼働を接続する必要がある。現在の全道路被覆経路の約88時間は除雪車の作業と回送の指標で、このモデルの累積ダンプ車両時間とは別。単純に足して除排雪完了時間にはできない。
