# 広域の事業者・車両割当

**現在の方式は[区域と直行経路の改善](direct_routing.md)。** 以下の作業単位ごと帰庫・全台への逐次直接割当は比較用の旧方式です。現行の全社方式は区域境界と連続経路を調整し、最後に帰庫します。

2026年9月8日更新。現在の主画面は広域道路を4社で分担する配車で、八軒実証への限定を外した。初期地図は全社台数で区域調整した方式の会社別担当色で、事業者マーカーを選ぶと車両別の作業・回送経路になる。所在地の近さだけで区域を作る会社担当固定方式は比較用に切り替えて表示する（台数を考慮しないため、3台のKRSが36%、4台のサツイチが22%の区間を持ち、全社完了300時間の原因になる）。

## 表示・割当方式の追加更新

事業者は「業1〜業4」の番号付きマーカーで、選択欄・凡例・台帳と対応する。既存融雪施設はDC候補と独立して表示を切替できる。地図の空白・道路・事業者以外の地点をクリックすると、車両フォーカスを解除して全社の担当表示へ戻る。

## 画面操作（2026-09-08 改良）

- 事業者マーカーのクリックは選択とポップアップのみで、地図の位置・ズームは動かない。ホバーは強調表示だけ。地図の移動は凡例の「この表示範囲に合わせる」「全社の範囲に合わせる」、または「出発点と往復経路を表示」を押したときだけ行う。地図の空白クリックで全社表示へ戻す動作は廃止し、凡例の「全社表示に戻る」に置き換えた。
- 全車両表示の開始点マーカー（番号付きの丸）をクリックすると、その車両の順序・方向・経過時間の表示に直接切り替わる。経路線のポップアップと、全社表示の会社担当色のポップアップにも切替ボタンを置いた。車両表示中は「全車両に戻る」で戻る。開始点が事業者所在地と重なる場合に隠れないよう、車両表示中は開始点マーカーを事業者マーカーより手前に描く。
- 事業者マーカーのクリックはポップアップを開かず、選択した会社の所在地・採用台数・公表保有機械・根拠を「事業者別の経路」節の先頭パネルに表示する。マーカーのホバーは会社名のツールチップのみ。
- 開始点が近い車両の車Nタグは、画面上で重なる場合に小さな輪状に並べ、どれもクリックできるようにした（ズームごとに再配置）。
- 車両表示中に地図の何もない所をクリックすると全車両表示に戻る（ポップアップを閉じるクリックは除く）。地図右上に現在の会社・車両と「◀ 全車両に戻る」「◀ 全社表示に戻る」を常時表示する。作業をクリックしても画面はスクロールしない。
- 地図のラベルは種別で統一した。事業者＝業N、DC候補＝DCN、既存融雪施設＝融N、車両の作業開始点＝車N（いずれも角丸）。丸数字は選択車両の作業順序だけに使う。
- 車両表示中も他車両の開始点を薄い車Nで残し、クリックで切り替える。凡例と作業順序パネルの車両チップ、「← 車N／車N →」ボタンでも移動できる。
- 車両を1台選ぶと、経路の色が出発からの経過時間（0〜2、2〜4、4〜6、6時間超）、開始点の番号が作業順序、矢印が進行方向になる。経過時間は各区間の形状から作業8km/h・回送20km/hで積算しており、配車データの時間と一致する。
- 「選択車両の作業順序と経過時間」パネルに作業ごとの開始・完了時刻、作業距離、回送距離、6時間以内かを表示する。行を選ぶと地図で該当作業を強調し、「地図で見る」で移動する。スライダーで経過時間を絞ると、その時点までに開始しない作業は薄く表示する。
- 全社表示の凡例は会社名をクリックすると表示の切替、未割当区間もチェックで切替できる。方式切替や台数変更をしても視点は維持する。
- 融雪施設・DCの「地図で見る」は、地図が画面外にあるときだけスクロールする。

八軒の旧パネルをHTMLから削除し、旧道路・仮設待機点・1〜8台計算の初期化も画面のJavaScriptから除いた。現在の `web/data.js` には旧analysis/roads/routesを含めない。過去の取得原本・計算ファイルと旧スクリプトは再現用に保存している。現在の基本データは `python scripts/build_dashboard.py` で生成する。

「全事業者・全30台へ直接割当」を割当方式に追加。会社を先に決めず、各車両の累積時間・候補会社の往復時間から `車両の完了予測時間＋0.2×今回の回送時間` を最小にする候補へ、長い作業単位から割り当てる。会社ごとに同じ出発点と性能を仮定するため、各社の最も空いた車両を候補にすることは全30台からこの式の最小候補を選ぶことと等価。全体最適性の保証はない。

旧2行は本書執筆時のモデル。中間版は帰庫制約を外した段階、現行は車両ごとの担当を飛び地のない区域にして区域別に郵便配達人問題を解いた段階で、いずれも[区域と直行経路の改善](direct_routing.md)に記載。画面に表示される値は現行。以下の節の156時間前後の値は旧モデルの記録として残す。

両方式の割当被覆は421,029方向区間、未割当10,087区間、作業重複ゼロ。両方式とも標準台数だけを計算し、画面の台数選択は固定表示にする（台数を変えた全経路を持つと画面データが131MBになるため）。画面は全社方式のデータを最初に読み込み、会社担当固定方式のデータは初回の方式選択で読み込んで再選択では再利用する。

札幌市のOSM行政界を取得して黒破線で表示。4社の公開所在地がすべて行政界内にあることを座標で確認した。**市外に出ているのは配車対象の道路であり、4社の所在地ではない。** 対象は矩形で取得した近郊込みの道路で、札幌市だけの除雪対象にはまだ限定していない。市外担当は実契約の根拠ではない。市境原本・取得日時・ハッシュは `data/raw/sapporo_boundary.json` と `data/boundary_source.json`。OSM境界は法的な境界確定資料ではない。

追加再計算：`python scripts/build_boundary.py`、`python scripts/run_dispatch.py --joint`。全30台方式の成果物は `data/processed/joint_dispatch*.json` / `.geojson` / `.json.gz`、画面用は `web/joint-dispatch-data.js`（初期読込）。会社担当固定方式の画面用は `web/dispatch-data.js`（選択時読込）。

現行の会社担当固定方式は所在地への道路上の近さだけで区域を決めるため、台数の少ないKRS・サツイチに広い区域が集まり全社完了が297.03時間まで延びる。全社方式は区域境界を調整してこれを89.34時間に抑える（担当区間は東洋152,534・鹿島197,995・サツイチ40,376・KRS30,124）。

時間は作業8km/h、回送20km/h、休憩なしの計算。6時間以内の実配車としては不成立である。対象道路自体が市域を覆う矩形と近郊のOSM道路で、市公式除雪対象路線と同一ではない。4社の保有数は札幌全体の機械数ではないため、この30台の不足を札幌全体の不足と読み替えない。

## 計算手順と適用範囲

1. 元の広域作業対象を保持し、回送用にtrunk・trunk_link・serviceの道路12,784 waysを追加取得。motorroad=yesの追加道路、accessが不許可の道路は除外。機種別の法的・物理的通行可否、旋回制限は未確認。
2. 4社の住所代表点を最寄りの道路ノードへ接続し、有向道路上で往路・復路の最短時間木を計算。所在地の代表点と道路ノードの差は、東洋192m・鹿島49m・サツイチ56m・KRS49m。入口までの未確認区間は走行時間に未算入。
3. 既存の広域閉路を約2時間の作業単位に分割。これまで成分間で未計算だった599区間は個別作業として追加。
4. 作業時間の長い単位から、`(既割当時間＋今回の作業・回送時間)/標準台数＋0.2×今回の回送時間` が小さい会社へ割当。往復到達可能な会社だけを比較する。係数0.2は負荷均衡と回送時間を両方考慮する設計上の仮定で、最適化した実測係数ではない。
5. 会社内では作業時間が長い単位から、その時点の累積時間が最も短い車両へ配分する。各作業単位の終わりに出発道路ノードへ戻る。長時間順の近似配分で、単位間の直行による回送削減は未実装。

各社の台数変更は固定された広域担当区間の再配分。1〜10、1〜13、1〜4、1〜3台の計30シナリオを持つ。他社の担当は変わらず、各区間は必ず同じ会社が作業する。仮定の機種上限は前段の公開台数資料と同じで、ダンプ・大型ロータリ・小型ショベルを同じ作業車として合算しない。

これは負荷均衡を含む近似配車で、最小総費用や全体最適性の保証はない。実契約地区・実車庫・当日稼働台数・雪量・車種別速度を接続した運用計画ではない。現在の遠距離回送を含む総時間を、そのまま必要車両数の確定値に換算しない。

## 検証と出力

生成時に、全割当区間の作業重複ゼロ、未割当との完全な区分、各作業単位の道路方向・連続性・出発道路ノードへの帰着を検証。30シナリオすべてで作業単位の欠落と重複がないことを確認した。

- `data/processed/dispatch_summary.json`：全体の割当検証結果
- `data/processed/dispatch.json`：会社別担当・車両別配分・共有する経路形状
- `data/processed/dispatch_ordered_routes.json.gz`：原本道路キーを持つ作業単位ごとの順序付き経路。各シナリオの車両はdispatch.jsonのtrip_ids順にこれらを連結する
- `data/processed/dispatch_unassigned.geojson`：未割当道路と理由
- `data/transit_roads_source.json`：回送道路の取得クエリ・日時・ハッシュ

```powershell
python scripts/expand_roads.py --transit
python scripts/run_dispatch.py
python -m unittest discover -s tests -v
```

画面用形状は小数6桁に丸め、距離と時間は丸め前の値で計算。画面用データは道路と経路が同じ道路頂点を共有することを利用し、座標表（`web/nodes-data.js`、約20.8万点の整数オフセット）を1つだけ持ち、道路も経路も頂点番号の列で表す（`scripts/build_web_geometry.py`）。`data/processed` のJSONは従来どおりGeoJSON座標で、画面側（`web/app.js` の decodeRoutes / decodeRoads）が読込時にGeoJSONへ戻す。初期読込は37.8MBから15.4MB（gzip後5.9→4.0MB）になった。八軒実証のファイルは比較・再現用に保持しているが、主画面の配車と地図には使用しない。
